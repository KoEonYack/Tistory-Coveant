## 시작하며

2026년의 AI 패러다임은 멀티 에이전트라고 할 수 있습니다.

JUMP 프로젝트를 통하여 Spring Boot 3.0.13 → 3.5, JDK 21 → 25 마이그레이션을 Claude Code를 활용해 진행하고 있습니다.

Spring Boot 3.x 마이그레이션은 수백개의 자바 파일에 SpringBoot 3.5 호환 코드 작성, Spring Security 전환, 의존성 버전 충돌 등 에러가 수십 개씩 동시에 터지는 작업입니다. 거기에 JDK 25까지 함께 올리는 작업이었습니다.

> 싱글 에이전트 vs 멀티 에이전트

이런 대규모 작업에 분석 Agent, 수정 Agent, 검증 Agent와 같이 역할별 멀티 에이전트를 구성했다는 사례가 많습니다. 그러나 싱글 에이전트로 작업을 하였고 그렇게 하지는 않았습니다.

그 근거에 대해서 엔트로픽의 [Building multi-agent systems: when and how to use them (2026.01.23)](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) 바탕으로 작성해 보겠습니다.

## 작업 개요

---

### 엔트로픽이 직접 겪은 것

본 글의 핵심 메시지는 간단합니다.

> "At Anthropic, we've seen teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results."
> 
> (엔트로픽이 목격한 바에 따르면, 많은 팀이 수개월 동안 정교한 멀티 에이전트 아키텍처를 구축하는 데 매진하지만, 결국 단일 에이전트의 프롬프트를 개선하는 것만으로도 동일한 결과를 얻을 수 있다는 사실을 뒤늦게 깨닫곤 합니다.)

엔트로픽 내부 팀들이 몇 달 동안 정교한 멀티 에이전트 아키텍처를 직접 구축해봤는데, 결국 싱글 에이전트에서 프롬프트를 잘 설계하는 것만으로 동등한 결과를 얻을 수 있었다는 겁니다.

글에 의하면, 멀티 에이전트가 싱글 에이전트보다 확실히 유리한 경우는 세 가지뿐입니다.

**1. Context Pollution**
- 이전 작업의 정보가 쌓여 이후 판단을 오염시킬 때.
- 고객 주문 이력 2,000토큰이 컨텍스트에 쌓인 채로 기술 문제를 진단해야 하는 경우.

**2. Parallelization** 
- 서로 독립적인 작업을 동시에 처리해야 할 때.
- 아시아 시장 트렌드와 유럽 시장 트렌드를 동시에 조사하는 것처럼, 결과가 서로에게 영향을 주지 않는 경우.

**3. Specialization**
- 도구가 20개 이상이거나 완전히 다른 도메인 전문성이 필요할 때
- CRM API, 마케팅 자동화 API, 메시지 플랫폼 API를 하나의 에이전트에게 몰아주면 혼선이 생기는 경우.

이 세 가지 조건이 없다면, 멀티 에이전트는 오버헤드만 추가합니다.

## JUMP 프로젝트에 대입

### 1. Context Pollution

이번 마이그레이션은 하나의 맥락이 처음부터 끝까지 이어지는 작업입니다. OpenRewrite 실행 결과를 바탕으로 의존성을 수정하고, 그 결과로 발생한 컴파일 에러를 분석하고, 파일을 고치고, 다시 빌드하는 순환 구조입니다.

각 단계는 이전 단계의 컨텍스트를 그대로 필요로 합니다. 예를 들어 SecurityConfig.java를 수정할 때, 에이전트는 이 파일이 Pre-authenticated 방식을 쓰고 있다는 것, CSRF 설정이 어떻게 되어 있는지, 직전 빌드에서 어떤 에러가 났는지를 모두 알고 있어야 정확한 수정이 가능합니다. 이를 에이전트 간에 나눴다면 핸드오프마다 맥락이 희석되었을 겁니다. 글에서 귓속말 게임(telephone game)이라 부르는 상황이빈다.


> [!NOTE]  
> 귓속말 게임 현상 (The Telephone Game)이란?
> 
> 정보를 한 에이전트에서 다른 에이전트로 넘길 때마다 정보의 정확도가 떨어지는 현상입니다. 귓속말 게임을 하면 첫 사람이 전달한 문장이 마지막 사람에게 가면 완전히 다른 말이 되어 있습니다. 
> 에이전트 간의 인수인계가 잦아질수록, 처음에 의도했던 복잡한 맥락과 디테일이 조금씩 깎여 나가 결국 엉뚱한 결과물이 나오게 됩니다.

------


### 2. Parallelization

빌드 → 에러 분석 → 수정 → 재빌드의 루프는 본질적으로 순차적입니다. 이전 빌드 결과 없이는 다음 수정을 결정할 수 없습니다. 병렬화할 수 있는 독립적인 작업 단위가 없었습니다.

------

### 3. Specialization

사용한 Tool은 Bash, Read, Edit, Write, Grep, Glob, WebSearch 7개입니다. 모두 같은 도메인(코드 수정)에 속하고, 20개 기준에 한참 못 미칩니다. 완전히 다른 전문성이 필요한 분리 지점도 없었습니다.


------

## 실제 구성 방법

Claude Code의 SKILL 기능을 활용해 세 개의 파일로 전체 작업을 설계했습니다.

### 1. CLAUDE.md — 프로젝트 컨텍스트

프로젝트 루트에 두는 파일로, 에이전트가 모든 세션에서 자동으로 읽는 컨텍스트입니다. 에이전트가 매번 물어보지 않아도 되는 프로젝트 고유 지식을 한 곳에 모았습니다.

```markdown
# PCWEB-NEW 프로젝트

## 기술 스택
- Spring Boot: 3.0.13 (→ 3.5 마이그레이션 진행 중)
- JDK: 21 (→ 25 마이그레이션 진행 중)
- cores 의존성: sb35-SNAPSHOT 사용 (SB 3.5 전용 아티팩트)
- WAR 패키징 유지

## 주의사항
- 비즈니스 로직 변경 금지 (API 호환성만 유지)
- javax.* 중 JDK 기본 API(javax.imageio 등)는 변환 대상 아님
- Frontend 빌드는 Java 마이그레이션과 무관, 변경 불필요
```

이 파일 덕분에 에이전트는 매번 프로젝트에 대해서 설명받을 필요가 없습니다.

---

### 2. migrate-sb35 SKILL — 마이그레이션 전체 흐름

SKILL은 Claude Code에서 `/migrate-sb35`처럼 슬래시 명령으로 실행하는 작업 레시피입니다. 전체 마이그레이션 파이프라인을 4개 Phase로 정의했습니다.

```txt
Phase 1: OpenRewrite 자동 마이그레이션
  → UpgradeSpringBoot_3_5 레시피 실행 후 설정 제거

Phase 2: 수동 의존성 업그레이드
  → Spring Boot 버전, JDK 버전, 사내 라이브러리 버전 업데이트

Phase 3: 빌드 루프 (컴파일)
  → ./gradlew clean build -x test -x installFrontend -x assembleFrontend
  → 에러 분류 → 수정 → 재빌드. BUILD SUCCESSFUL까지 반복.

Phase 4: 빌드 루프 (테스트)
  → 실패한 테스트만 집중 수정
```

SKILL 안에 명시한 핵심 규칙은 이렇습니다.

```
- 멈추지 마 — BUILD SUCCESSFUL까지 반복
- 질문하지 마 — 에러 발생 시 스스로 판단하고 수정
- 중간 보고 없음 — 최종 결과만 보고
- 비즈니스 로직 변경 금지 — API 호환성만 맞추기
- 같은 에러 3회 반복 시 — 접근 방식 변경
```

이것이 핵심입니다. 멀티 에이전트로 작업을 수행하지 않고, 대신 싱글 에이전트가 스스로 판단하고 반복할 수 있도록 프롬프트로 행동 방식을 정밀하게 설계하는 것. 아티클이 말하는 "improved prompting on a single agent"의 실제 적용입니다.

---

### 3. build-analyzer Agent — 유일하게 분리한 지점

이 부분이 가장 흥미롭습니다. 빌드 에러 분석은 `build-analyzer`라는 별도 Agent로 분리했는데, 이것은 앞서 말한 역할 나누기와 다릅니다.

빌드 에러 로그 50~200줄은 분석 후에는 필요 없는 정보입니다. 메인 세션에 계속 쌓이면 이후 수정 판단에 노이즈가 됩니다. 분석 Agent가 에러 로그를 처리하고 수정이 필요한 파일 경로와 방법만 요약해서 반환하는 구조는 정확히 **Context Pollution 방지**를 위한 올바른 분리입니다.

글에서는 이렇게 말합니다.

> The agent receives only the 50-100 tokens it actually needs, keeping context focused.
>
> (에이전트는 실제로 필요한 50~100개의 토큰만 전달받기 때문에, 핵심 맥락에만 온전히 집중할 수 있습니다)

빌드 에러 분석은 그 자체로 완결되고, 결과만 컴팩트하게 전달할 수 있는 작업이기 때문에 분리가 의미 있었습니다.

```markdown
# build-analyzer Agent의 역할

1. ./gradlew clean build 실행
2. 에러를 컴파일/의존성/설정/Security 카테고리로 분류
3. 관련 파일 조사 (소스, build.gradle, application.yml)
4. 수정이 필요한 파일과 구체적인 수정 코드만 반환
```
에러 원문 로그는 반환하지 않습니다. 파일 X의 Y라인을 이렇게 바꾸라는 내용만 전달합니다.

## 토큰과 비용 이야기

아티클에서 주목한 수치가 있습니다.

> "In our testing, multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks."
>
> (자체 테스트 결과, 동일한 작업에 대해 멀티 에이전트 방식은 싱글 에이전트 방식보다 보통 3배에서 10배 더 많은 토큰을 소모합니다.)

동일한 작업을 멀티 에이전트로 진행하면 토큰을 3~10배 더 씁니다. 각 에이전트가 자신의 컨텍스트를 따로 유지해야 하고, 에이전트간 메시지 교환 자체가 토큰을 소비하며, 핸드오프할 때마다 결과를 요약해서 전달해야 합니다.

실제로 기획/실행/검토/반복 역할을 나눠 실험한 팀의 결과도 소개됩니다. 실제 작업보다 Agent 간 조정에 더 많은 토큰이 소비되었다고 합니다.

## 추가 조언 - 도구가 많아지는 상황

글에서는 Tool이 많아지는 상황에 대한 해법도 제시합니다.

AI 모델에게 Tool을 제공한다는 것은, 프롬프트 안에 그 도구가 무엇을 하는지, 어떻게 쓰는지를 아주 자세하게 적어준다는 뜻입니다.

도구가 20개라면, 매 대화마다 이 20개의 사용법을 전부 읽어야 합니다. 따라서 토큰 낭비가 생깁니다. 선택지가 너무 많으면 AI도 헷갈리기 시작합니다. 비슷한 도구 사이에서 엉뚱한 것을 고르거나, 질문의 맥락을 놓치는 혼란스러운 현상이 발생합니다. 이 과정을 통해서 응답 결과는 느려집니다.

에이전트에게 Tool을 20개 이상 주기 전에, 필요할 때 동적으로 Tool을 검색하는 **Tool Search Tool** 방식을 먼저 시도해볼 것을 권장합니다. 이 방식으로 토큰 사용량을 최대 85%까지 줄인 사례도 있다고 합니다. 

이 수치는 프롬프트 다이어트의 결과입니다.

만약 도구 1개당 설명이 500토큰이고 도구가 50개라면, 기본 프롬프트만 25,000토큰입니다. 그러나 Search Tool 방식을 쓰면 AI는 검색 도구(약 100토큰) + 검색 결과(약 1,000토큰) 정도만 사용합니다.

멀티 에이전트보다 싱글 에이전트가 Tool 전략을 먼저 최적화하는 것이 우선순위입니다.

## 만약 멀티 에이전트로 했다면?

역할 기반으로 나눴다면 이런 구성이 됩니다.

```
분석 에이전트 → 수정 에이전트 → 검증 에이전트 → Orchestrator
```

이 구성의 문제는 구체적인 시나리오에서 드러납니다.

분석 에이전트가 "SecurityConfig.java의 filterChain 메서드 시그니처를 수정하라"고 전달합니다. 수정 에이전트는 이 파일을 엽니다. 그런데 이 파일이 왜 Pre-authenticated 방식을 쓰는지, 어떤 다른 컴포넌트와 연계되어 있는지, 직전 빌드에서 다른 어떤 파일들을 이미 수정했는지를 모릅니다. 맥락 없는 수정은 새로운 에러를 만들고, 그 에러를 다시 분석 에이전트로 보내는 루프가 시작됩니다.

실제 수정보다 에이전트 간 메시지 교환이 더 많아지는 상황. 아티클이 정확히 경고한 패턴입니다.

반면 단일 에이전트는 "이 파일을 왜 이렇게 설계했는지", "직전에 어떤 수정을 했는지", "같은 패턴이 다른 파일에도 있는지"를 하나의 컨텍스트 안에서 추적할 수 있습니다.

## 마치며

에이전트 설계에서 중요한 것은 겉으로 보이는 복잡함이 일을 잘 해내지는 않습니다. 실제로 일을 잘 수행하는 방식을 선택하는 것입니다.

이번 마이그레이션에서 선택한 방식은 단순했습니다. CLAUDE.md로 프로젝트 컨텍스트를 고정하고, SKILL로 반복 작업을 자동화하고, 컨텍스트 오염이 발생하는 지점 하나에만 별도 에이전트를 뒀습니다. 그 단순함은 에이전트에 대한 특성을 고민하여 설계하였습니다.
