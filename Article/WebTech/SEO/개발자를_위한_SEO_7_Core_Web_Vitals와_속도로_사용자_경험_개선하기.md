## 시작하며

<br />

SEO 점검을 하다 보면 Lighthouse 점수 하나만 보고 배포를 판단하기 쉽습니다. 하지만 실험실 환경에서 한 번 측정한 점수와 실제 사용자가 겪는 속도는 다를 수 있습니다.

<br />

속도 개선의 목적은 점수를 맞추는 일이 아니라, 사용자가 내용을 볼 때까지 기다리지 않고 안정적으로 상호작용하게 만드는 일입니다. Core Web Vitals는 이 경험을 측정하는 공통 언어로 쓸 수 있습니다.

<br />

이번 글에서는 LCP, INP, CLS를 해석하는 방법과 변경 효과를 확인하는 방법을 정리합니다.

<br />
<br />
<br />

## 점수보다 현장 데이터가 먼저다

<br />

PageSpeed Insights에는 두 종류의 데이터가 있습니다.

<br />

```text
필드 데이터
실제 사용자의 브라우저에서 수집된 경험 데이터다.
기기, 네트워크, 지역의 차이가 반영된다.

랩 데이터
정해진 환경에서 도구가 한 번 실행해 얻은 진단 데이터다.
원인을 찾고 개선 전후를 비교하는 데 좋다.
```

<br />

필드 데이터가 있다면 먼저 이것을 봅니다. 실제 사용자가 겪는 문제를 보여 주기 때문입니다. 다만 트래픽이 적은 새 페이지에는 필드 데이터가 없을 수 있으므로, 이때는 랩 데이터와 브라우저 성능 프로파일을 함께 사용합니다.

<br />

검색 유입이 많은 페이지, 전환이 중요한 페이지, 모바일 사용 비중이 높은 페이지부터 우선순위를 정하면 됩니다. 모든 URL을 같은 수준으로 최적화하려고 시작하면 중요한 병목을 놓치기 쉽습니다.

<br />
<br />
<br />

## LCP는 가장 중요한 내용이 보이는 시점이다

<br />

LCP(Largest Contentful Paint)는 화면에서 가장 큰 콘텐츠 요소가 그려지는 시점에 가깝습니다. 기사라면 제목이나 대표 이미지, 상품 페이지라면 상품 이미지가 LCP 후보가 될 수 있습니다.

<br />

LCP가 느릴 때는 "이미지를 압축하자"부터 시작하지 말고, 어느 구간이 오래 걸리는지 나눠 봐야 합니다.

<br />

```text
1. 서버가 HTML을 보내기까지 오래 걸린다.
2. 브라우저가 중요한 이미지 주소를 늦게 발견한다.
3. 이미지 파일을 내려받는 데 오래 걸린다.
4. 내려받은 뒤 디코딩하거나 화면에 그리는 시간이 길다.
```

<br />

대표 이미지는 지연 로딩 대상이 아닙니다. 첫 화면의 중요한 이미지를 `loading="lazy"`로 두면 브라우저가 발견을 늦출 수 있습니다. 이미지에는 실제 표시 비율에 맞는 크기, 적절한 포맷, 명시적인 `width`와 `height`를 제공하세요.

<br />

```tsx
import Image from 'next/image'

<Image
  src={post.coverImage}
  alt={post.title}
  width={1200}
  height={630}
  priority
  sizes="(max-width: 768px) 100vw, 800px"
/>
```

<br />

이 예시에서 `priority`는 첫 화면에서 실제로 중요한 이미지에만 사용합니다. 모든 이미지에 적용하면 브라우저의 우선순위 판단을 방해할 수 있습니다.

<br />
<br />
<br />

## INP는 클릭 뒤에 늦게 반응하는 문제다

<br />

INP(Interaction to Next Paint)는 사용자의 입력이 화면 변화로 이어지기까지의 반응성을 측정합니다. 버튼을 눌렀는데 로딩 표시나 다음 상태가 늦게 보이는 상황을 떠올리면 됩니다.

<br />

INP가 나쁘다면 보통 긴 JavaScript 작업이 메인 스레드를 오래 점유하고 있습니다. 다음 항목부터 확인하세요.

<br />

- 첫 화면에 필요 없는 라이브러리를 함께 내려받고 있지 않은가
- 클릭 핸들러 안에서 큰 배열을 반복하거나 복잡한 계산을 하지 않는가
- 스크롤, 입력 이벤트마다 동기적으로 상태를 많이 갱신하지 않는가
- 분석 도구나 채팅 위젯이 초기 로딩을 막고 있지 않은가

<br />

큰 작업은 더 작은 단위로 나누고, 화면과 관계없는 연산은 Web Worker나 서버로 옮길 수 있는지 검토합니다. 단순히 `setTimeout`으로 미루는 방식은 문제를 숨길 뿐, 사용자 경험을 보장하지 못할 수 있습니다.

<br />
<br />
<br />

## CLS는 화면이 움직이는 문제다

<br />

CLS(Cumulative Layout Shift)는 사용자가 읽으려는 순간 화면 요소가 밀려나는 현상을 측정합니다. 이미지, 광고, 임베드, 웹 폰트가 흔한 원인입니다.

<br />

이미지와 동영상에는 크기나 `aspect-ratio`를 미리 정해 둡니다. 외부 광고나 동적 위젯도 필요한 공간을 먼저 확보해야 합니다.

<br />

```css
.video-frame {
  aspect-ratio: 16 / 9;
}

.ad-slot {
  min-height: 250px;
}
```

<br />

콘텐츠 위쪽에 나중에 배너를 끼워 넣는 방식도 피해야 합니다. 사용자가 이미 읽기 시작한 화면을 밀어 내는 변화는 CLS 수치와 별개로도 불편합니다.

<br />
<br />

## 캐시는 공개 페이지와 개인화 페이지를 분리할 때 강해진다

<br />

문서, 블로그 글, 공개 상품 정보처럼 모든 사용자에게 같은 HTML을 제공하는 페이지는 CDN 캐싱이 특히 효과적입니다. 반대로 로그인 정보나 장바구니처럼 사용자마다 달라지는 값까지 같은 응답에 섞으면 캐시를 안전하게 쓰기 어렵습니다.

<br />

공개 본문은 캐시 가능한 HTML로 제공하고, 개인화된 작은 영역만 별도 API나 클라이언트 요청으로 가져오는 구조를 검토하세요. 이렇게 하면 속도와 개인정보 보호를 함께 다루기 쉬워집니다.

<br />

배포 후에는 응답 헤더와 실제 캐시 동작을 확인합니다.

<br />

```bash
curl -sI https://example.com/posts/seo-basics \
  | rg -i 'cache-control|age|x-cache|server-timing'
```

<br />

헤더 이름은 CDN마다 다릅니다. 중요한 점은 두 번째 요청에서도 원본 서버를 다시 거치고 있지는 않은지, 갱신 뒤 오래된 콘텐츠가 과도하게 남지는 않는지입니다.

<br />
<br />

## 정리

<br />

속도는 SEO와 별개의 장식이 아닙니다. 사용자가 콘텐츠에 도달하고, 읽고, 상호작용하는 과정 자체입니다. LCP는 중요한 내용의 표시, INP는 입력 반응, CLS는 화면 안정성에 집중하도록 도와줍니다.

<br />

필드 데이터로 우선순위를 정하고, 랩 데이터로 원인을 좁히세요. 대표 이미지, 불필요한 JavaScript, 크기가 없는 동적 영역처럼 영향이 큰 문제부터 고치면 개선 효과를 확인하기 쉽습니다.
